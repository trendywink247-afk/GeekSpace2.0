=== LOGIC ISSUES ===
1. API key not saved: AgentStep local useState `apiKey` is never included in getStepData(2).
   User enters their OpenRouter key but it is silently discarded on Continue.

2. Back button hidden on Review step: step > 0 && step < STEPS.length - 1 means the back
   button is not shown on the last step (Review). User cannot go back to edit from Review
   without skipping or reloading.

3. Refresh behavior gap: onboarding.step (from store) is initialized from user.onboardingStep
   (server value). The PATCH saves step N+1 (the next step number), so after refreshing the
   user lands on the step they were heading to. This is actually correct behavior but is
   confusing: the wizard state (filled fields) is in-memory only and lost on refresh.

4. Step indicator off-by-one: PATCH /onboarding/:step is called with step+1 (next step number),
   but step indices in the wizard are 0-based (0-5), while the server validates 1-6. This is
   correct but means the server's step 6 = client's step 5 (Review). Consistent but fragile.

5. canAdvance for Bio step: validation allows bio.length === 0 (empty) OR bio.length >= 10.
   This means an empty bio passes Continue, but a 1-9 char bio blocks it. Inconsistent UX —
   either require bio or truly make it optional (no minimum).

6. Username uniqueness not checked client-side: PATCH /onboarding/1 returns 409 if username
   taken, but the wizard catches this in a generic finally block that just clears isSaving.
   The error from the server is thrown but not surfaced to the user — they just see the button
   stop spinning with no feedback.

7. No error handling on handleNext: saveOnboardingStep errors are swallowed (try/finally only
   resets isSaving). If the server returns an error, the step still advances visually.

8. estimatedTime calculation: timePerStep is hard-coded at 0.5 min. At step 5 (Review),
   remainingSteps = 0, so estimatedTime = 0.5 (max). This shows "~0.5 min remaining" on
   the Review step which is inaccurate — user is done.

9. WhatsApp QR polling: interval runs every 3s indefinitely. If user navigates away from
   step 4 while polling is active, the interval is not cleared (cleanup only runs on
   whatsappPolling=false). Could accumulate if user returns to step 4 repeatedly.

=== SERVER ROUTES USED ===
PATCH  /api/auth/onboarding/:step  — per-step save (steps 1-6; called on each Continue click)
POST   /api/auth/onboarding/complete — marks onboarding done, called on Launch
GET    /api/auth/me — re-fetches user after complete (to update onboardingCompleted flag)
POST   /api/agent/generate — AI magic bio/portfolio generation (BioStep, PortfolioStep)
POST   /api/integrations/telegram/link — get Telegram deep link
GET    /api/integrations/telegram/status — check if Telegram linked
DELETE /api/integrations/telegram/link — unlink Telegram
POST   /api/integrations/whatsapp/qr — generate WhatsApp QR session
GET    /api/integrations/whatsapp/qr/:sessionId/status — poll WhatsApp link status
DELETE /api/integrations/whatsapp/link — unlink WhatsApp

NOTE: There is also a POST /api/auth/onboarding (different from PATCH) that the wizard does NOT
call. That older endpoint accepts profile+agentMode in one shot. The wizard exclusively uses the
per-step PATCH flow, which is correct.
