=== LOGIC ISSUES ===
1. The Telegram dialog is rendered as an inline Card that pushes content down, not a modal. On long pages, the dialog may not be in view after being opened. No scroll-into-view on open. On mobile, user may not notice it appeared above the grid.

2. The Telegram polling uses exponential backoff (1s → 2s → 4s → 5s cap with ±500ms jitter), but telegramPollAttempts increments indefinitely — there is no max poll attempt limit. If the user leaves the dialog open without completing the link, polling continues indefinitely until closeTelegramDialog() is called.

3. connectingId is set to type but NOT cleared in the finally block for the telegram flow — it returns early before the finally. This means the Telegram "Connecting..." spinner on the button persists even after the dialog opens (since setConnectingId(null) is only in the catch block for telegram, not after dialog open). The finally { setConnectingId(null) } only runs for non-telegram/non-email types.
   Fix: move setConnectingId(null) into the telegram success/open path.

4. For email, handleConnect returns early after setting emailDialog=true but before the finally block. The finally block sets connectingId(null) after the return, so the button loading state may persist briefly. Actually: `return` inside try exits the try, the finally still runs. This is actually fine.

5. The integration health check fires on mount and every 60s for ALL connected integrations simultaneously. If a user has many integrations, this creates N concurrent POST requests every minute. No throttling or staggering.

6. The "Avg Health %" stat is computed as: sum of connected integrations' health / connected count. This uses the health field from the integrations table, not the live health check results (healthStatus state). The displayed average could be stale.

7. The "Secure 100%" stat card is hardcoded. It does not reflect any real security state.

8. The invite URL is hardcoded as https://ai.geekspace.space/connect/${token} in the server route. For different domain deployments (agentin.chat) this would be wrong.

9. Disconnecting email (handleDisconnect) only calls updateNotificationEmail({ enabled: false }) — it does not clear the stored email address. On reconnect, the old address pre-populates.

10. The health dot (checking/healthy/unhealthy) overlaps visually with the status text on very narrow cards. No ARIA labels on the colored dot — screen readers cannot determine health state.

=== SERVER ROUTES USED ===
GET    /api/integrations                    — load all integrations (on DashboardApp mount + on closeTelegramDialog)
POST   /api/integrations/:type/connect      — connect non-Telegram/email integrations (fake connect for GitHub, Google Calendar, etc.)
POST   /api/integrations/:id/disconnect     — disconnect
POST   /api/integrations/telegram/link      — generate Telegram deep link / check if already linked
GET    /api/integrations/telegram/status    — poll for link completion + fetch username/lastPing
DELETE /api/integrations/telegram/link      — unlink Telegram
PATCH  /api/users/notification-email        — save/disable email notification address
POST   /api/integrations/:type/test         — health check (60s interval)
GET    /api/integrations/:type/ping         — latency ping on demand
POST   /api/integrations/invite             — generate invite link
GET    /api/integrations/events?limit=10    — integration event log

Routes available but NOT used by ConnectionsPage:
GET    /api/integrations/invites            — list existing invites (no UI to show them)
GET    /api/integrations/whatsapp/status    — WhatsApp status (not used since Coming Soon)
POST   /api/integrations/whatsapp/qr       — new QR-based WhatsApp linking (not wired)
