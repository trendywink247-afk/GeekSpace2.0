=== LOGIC ISSUES ===
1. The bottom "Delete all in {category}" button calls handleDeleteByCategory, which loops over filtered memories and calls handleDelete (window.confirm per item) for each one. This is double-problematic: (a) window.confirm blocks the thread for each item, creating a multi-confirm dialog flood if the category has 10+ entries, and (b) each delete is a separate HTTP request. The new bulk-clear modal (via the "x all" pills) uses the correct server-side batch endpoint. The old bottom button should be removed or wired to the same modal flow.

2. handleDelete uses window.confirm() which does not work in PWA standalone mode (some iOS/Android WebViews block it) and is visually inconsistent with the rest of the app's modal style. Should use the same custom modal pattern as the bulk-clear confirm.

3. The delete catch block is empty:
   try { await memoryService.delete(id) } catch { /* non-fatal */ }
   The memory is removed from local state regardless of API success/failure. If the server rejects the delete (e.g., auth failure, DB error), the UI shows it as deleted but it still exists on the server. On next page load, it reappears — confusing the user.

4. No pagination: all memories are returned in a single API call (GET /agent/memory). Looking at the server-side route, there's no limit parameter in the frontend call. For power users with hundreds of memories (AI accumulates them over time), this will cause slow load times and large data payloads.

5. No "Add Memory" form. While memories are primarily AI-extracted, there's no way for users to manually add important facts (e.g., "My timezone is IST"). The server supports POST /agent/memory with full create functionality, but there's no UI.

6. No "Edit Memory" functionality. Users can see and delete memories, but cannot correct wrong information the AI extracted. PUT /agent/memory/:id exists on the server but is not surfaced in the UI.

7. The category quick-filter pills and the category dropdown are duplicated controls — both control selectedCategory. Changing one does not reset the other's visual state (the dropdown still shows the old value if user clicked a pill). They are properly synced via shared selectedCategory state, but visually it can be confusing to have two ways to set the same filter.

8. The Avg Confidence stat is computed client-side: (sum of confidence / length * 100). This is accurate for the currently-loaded data. However, if only a subset of memories is loaded due to future pagination, this average would be misleading.

9. Category is extracted from the memory entries themselves — it comes from the AI memory extraction. There's no predefined set of categories, so the filter list dynamically reflects whatever categories the AI has created. Users cannot create custom categories.

10. The export downloads ALL memories in the current memories state (not just the filtered/visible ones). If the user has filtered to a category, they may expect the export to contain only that category's memories, but it exports everything.

=== SERVER ROUTES USED ===
GET    /api/agent/memory                    — load all memories (no pagination)
DELETE /api/agent/memory/:id               — delete single memory
DELETE /api/agent/memory/bulk?category=X  — bulk delete by category (via memoryService.bulkClear)

Routes available but NOT used by MemoryManagerPage:
POST   /api/agent/memory                   — create memory (no "Add" UI)
PUT    /api/agent/memory/:id               — update memory (no "Edit" UI)

How memory affects chat (server-side, not visible in UI):
  - buildMemoryContext(userId, userMessage) in agent.ts reads from DB and injects relevant memories into the system prompt for every /agent/chat call.
  - extractMemoriesWithAI() runs as a background task after each chat exchange to auto-extract new memories.
