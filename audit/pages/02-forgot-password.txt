=== LOGIC ISSUES ===
1. The server's /api/auth/forgot-password endpoint returns a generic message regardless of whether the email exists ("If that email is registered, you'll receive a reset link.") — this is correct anti-enumeration behavior. However, the frontend reads res.data.success and res.data.error: if the server always returns success-like JSON, the client always advances to the OTP step even if no email was sent. This means a user who enters a non-existent email will be stuck waiting for an OTP that never arrives, with no way to know why. The "Try again" back button handles recovery.
2. The server's /api/auth/forgot-password response structure does NOT match what the frontend expects: the server returns `{ message: "If that email..." }` but the frontend checks `res.data.success && res.data.error`. Since `res.data.success` is undefined (falsy) and `res.data.error` is also undefined, the condition `!res.data.success && res.data.error` is `true && false` → false, so the code falls through to `setChannel(res.data.channel || 'email')` and `setStep('otp')`. This works accidentally but the logic is fragile — any change to the server response format could break it.
3. The `requestPasswordReset` call passes channel `'auto'` hardcoded. This is fine but there's no UI option for users to choose their preferred reset channel (email vs Telegram). The 'auto' logic presumably picks Telegram if connected.
4. OTP inputs use maxLength={6} but the onChange handler handles single-digit AND paste (multi-char). The single-digit path only accepts one char, then auto-advances. This is correct but worth noting that maxLength=6 on a single box meant for 1 digit is slightly misleading — it's only used for paste detection (length > 1 triggers paste handling).
5. No resend timer is shown. After clicking "Try again" to go back to the email step, the user re-enters their email and can request a new code immediately. If the server has a rate limit on reset requests, the user could get a confusing error without explanation of the cooldown period.
6. Step indicator uses `['email', 'otp', 'password'].indexOf(step)` to determine completed steps. This hard-coded index comparison is functional but would break if step type order changed.
7. resetToken is stored in component state (React useState). If the user navigates away or refreshes during step 3, the resetToken is lost and they must restart from step 1. This is acceptable security behavior but worth documenting.

=== IMPROVEMENTS ===
HIGH — Fix the server/client response contract: The frontend checks `res.data.success` but the server returns `{ message: "..." }` with no `success` field. Either update the server to return `{ success: true, channel: 'email' }` or update the client to check `res.data.message` instead. The current code works by accident.
MED — Add a countdown timer on the OTP step showing remaining time until the code expires (10 minutes per the UI text). Auto-redirect or show a message when expired.
MED — Add a resend cooldown: After requesting a code, disable "Try again" for 60 seconds with a visible countdown to prevent spam and avoid confusing rate-limit errors.
MED — Show clearer messaging for non-existent emails: Since the API intentionally hides whether an email exists, add a note like "If you don't receive a code within 2 minutes, check your spam folder or try a different email."
LOW — Add password strength indicator (not just length/match checks) to help users choose stronger passwords.
LOW — Consider adding a "Show/Hide password" toggle on both password fields in step 3.
