=== LOGIC ISSUES ===
1. Schedule card shows "8:00 AM -- Idle Check-in" for the Idle Check-in type but the description says "Sent only if you have been inactive for 3 or more days" — the schedule label is misleading because this is not a fixed 8:00 AM delivery; it is conditional. The user cannot tell from this card when exactly they will receive it.
2. Both Daily Briefing and Idle Check-in show "8:00 AM" as their time — these are actually different proactive triggers running at different times server-side (the engine handles the logic), but both are labeled 8:00 AM which may confuse users who expect separate times.
3. The toggle is a custom inline HTML element (`<button>` with CSS classes) rather than the shadcn Switch component used elsewhere in the app — visual inconsistency with the rest of the design system.
4. `TYPE_LABEL` and `TYPE_COLOR` are initialized as empty Record objects and populated with imperative assignments (e.g., `TYPE_LABEL["daily_briefing"] = "Daily Briefing"`) rather than object literals — this is unusual style and makes the mappings harder to read/maintain.
5. The `getMsgIcon` function uses `if/else` comparisons but the returned type `typeof Bell` is the icon component — if an unknown message type arrives, it defaults to `Sunrise` icon (the default return), which could be misleading (should default to `MessageSquare` or a generic bell).
6. `formatDate` uses `en-IN` locale — this is the Indian English locale, not a user-configured locale. This hardcodes IST-style date formatting for all users regardless of their location.
7. On toggle failure, the error message ("Failed to update setting. Please try again.") appears in the error banner at the top of the page, but the toggle visual state is NOT rolled back — the toggle may briefly show the new state before the error clears it, or it may show the wrong state until the next full data refresh.
8. `fetchData` is called once on mount. After toggling, the toggle state is updated from the server response (`setEnabled(data.enabled)`) but the message log is NOT refreshed — this is fine since toggling doesn't create new messages.

=== SERVER ROUTES USED ===
GET    /api/proactive/log        — last 20 (or ?limit) proactive messages sent to user
GET    /api/proactive/settings   — reads proactive_enabled from users table
PATCH  /api/proactive/toggle     — enables or disables proactive messages (updates users.proactive_enabled)

Server-side engine: server/src/services/proactive-engine.ts — runs scheduled daily_briefing, overdue_alert, idle_check_in messages via cron/timer; delivers via Telegram. The proactive engine state is not exposed via additional API endpoints (e.g., no "trigger now" endpoint).
