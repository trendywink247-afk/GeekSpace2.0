=== LOGIC ISSUES ===
1. Username validation inconsistency: InvitePage strips hyphens (/[^a-z0-9_]/g) but
   ProfileStep during onboarding allows hyphens (/[^a-z0-9-_]/g). A username with a hyphen
   can be set during onboarding but cannot be entered on the invite page — the hyphen would
   be silently removed mid-typing.

2. No server-side invite code pre-validation in step 1: clicking Continue with a syntactically
   valid but semantically wrong code (e.g., a 4-char code that doesn't exist in the DB)
   proceeds to the full registration form. The user fills in all fields, submits, then gets
   the "Invalid invite code" error. This is a poor UX — a quick GET /api/auth/invite/validate
   call in step 1 would catch bad codes early.

3. Invite code case sensitivity: client uppercases with .toUpperCase() and server compares
   with .trim().toUpperCase(). This is consistent. However, if a user pastes a code with
   spaces around it, the trim only happens server-side. Client should trim before display.

4. No check if user is already logged in: if an authenticated user visits /invite, they can
   attempt registration. This would fail server-side (email/username already taken), but the
   UX should redirect them to /dashboard with a message instead of showing the registration form.

5. /terms and /privacy routes: the form links to these pages. If they don't exist in the
   router, clicking them would 404 or show a blank page — creating legal liability for a
   registration page that references non-functional ToS links.

6. Registration response: the signup endpoint returns user object without `onboardingCompleted`
   field (unlike login which includes it). After navigating to /dashboard, the app's auth guard
   should check onboardingCompleted — if it's undefined/null, behavior depends on the
   authStore's default. A newly-created user should be routed to /onboarding, not /dashboard.
   The navigate('/dashboard') here may bypass that guard.

7. Error state not cleared on step change: when going back from step 2 to step 1 (via "change"
   link), setError('') is called explicitly — this is correct. But if an error shows in step 1,
   then user proceeds to step 2, the step 1 error variable is cleared by setStep transition.
   This is fine; noting it as correct behavior.

=== IMPROVEMENTS ===

Priority HIGH — Verify /terms and /privacy routes exist in the router. If not, these must be
  created or the links updated to external URLs before this page can be used in production.

Priority HIGH — After signup, navigate to /onboarding not /dashboard. Newly registered users
  need onboarding and the signup response does not set onboardingCompleted=true.

Priority MED — Unify username character rules between InvitePage and ProfileStep (either
  both allow hyphens or neither does).

Priority MED — Add client-side trim of invite code before display and submission to prevent
  space-padded codes causing confusing validation failures.

Priority MED — Redirect already-authenticated users away from /invite to /dashboard.

Priority LOW — Show a character counter or hint on the username field explaining allowed
  characters (the silent stripping of hyphens will confuse users trying to type "john-doe").

=== SERVER ROUTES USED ===
POST /api/auth/signup — called on step 2 form submit. Accepts:
  { email, password, username, name?, invite_code }
  Returns { user, token } on success.
  Returns 403 if invite_code missing/invalid, 409 if invite already used or email/username taken.
  Internally: creates user, agent_config, features, subscription, portfolio, pico_agents,
  default integrations records, marks invite_code as used.

No other routes called. The page does not call any pre-validation endpoint for the invite code.
