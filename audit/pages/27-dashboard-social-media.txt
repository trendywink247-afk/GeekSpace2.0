=== LOGIC ISSUES ===
1. The Posts tab loads all plans sequentially in a loop (`for (const plan of res.data) { const planRes = await ... }`) — this is O(n) sequential API calls. For users with many plans, this creates significant load time and server pressure. Should use a dedicated /posts endpoint that aggregates across plans server-side.
2. No edit button on existing social accounts — users who need to update their webhook URL or rotate an access token must delete and recreate the account, losing post history association.
3. The plan-loading flow in ContentPlanTab auto-loads only the first plan (`plansRes.data[0]`) on initial load. If a user has multiple plans, they must manually click each one from the "Existing Plans" list — the active plan selection state is local only (setActivePlan) and resets on tab navigation.
4. `handleDeletePlan` has no confirmation dialog — immediately deletes the active plan and its items.
5. `loadData()` inside ContentPlanTab calls `socialMediaService.getPlans()` and `socialMediaService.getAccounts()` every time an action completes (generate, activate, delete) — the accounts list is re-fetched unnecessarily on plan operations.
6. Accessing token (access_token) is stored encrypted on the server but entered as a plain-text password input field — no guidance on token security, rotation policy, or expiry.
7. The Posts tab filter button renders item counts inline but the count for "all" filter button still shows nothing (only non-"all" filters get count badges in the code), which is slightly inconsistent.
8. Media ID is a free-text input (img-xxx or vid-xxx format) — no validation, no browse/picker for existing generated media. Users must know the internal ID format.
9. Status badge uses `item.status` directly but the `statusColors` map does not have an entry for "enabled" status — any unknown status falls through to `#6B7280` gray.
