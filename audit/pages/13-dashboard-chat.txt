=== MOBILE VIEW ===
Height: calc(100dvh-180px) — uses dvh (dynamic viewport height) which accounts for mobile browser chrome. This correctly prevents keyboard push issues.
The -180px leaves room for the dashboard header (56px), page padding, and bottom tab bar (approx 88px with safe area). Actual remaining space may be tight on small screens.
Input is at the bottom of the container (flex-col, input is flex-shrink-0). Messages area is flex-1 overflow-y-auto — scroll to latest works via scrollIntoView on messagesEndRef.
VoiceButton touch target: not explicitly checked here but min-w-[44px] should be enforced by the VoiceButton component.
No keyboard-push layout breakage expected due to dvh usage, but the -180px offset may need tuning on very small screens (e.g., iPhone SE at 375px width).
Clear chat and Voice toggle buttons are small (p-1.5) — touch target may be under 44px.

=== LOGIC ISSUES ===
1. No chat history persistence. Every page navigation to /dashboard/chat (or any route change and back) resets messages to []. Users lose their conversation context. There are server-side conversation logging endpoints (GET /agent/conversations) but ChatPage never calls them.

2. No streaming. The chat call is agentService.chat() which is a standard POST/await. LLM responses from Ollama can take 10-70 seconds. During this time the user sees only the typing dots with no partial text. A streaming implementation (POST /agent/chat/stream exists on the server) is available but not used in ChatPage.

3. Alt+V auto-listen: DashboardApp sets voiceListening=true (a local state) which only shows a toast for 200ms, then navigates to /dashboard/chat. ChatPage has no way to receive the "start listening" signal — it does not auto-start the VoiceButton on mount. The shortcut navigates correctly but does not automatically trigger voice listening.

4. The 'Response Time' stat referenced in the overview sidebar note also applies here: The chat page uses agentService.chat() which routes through POST /agent/chat. No per-request latency is displayed to the user.

5. The VoiceButton component is rendered even when voice.isSupported is false (based on isSupported prop). It should be hidden or replaced by a disabled state indicator when not supported.

6. Input placeholder text is "Listening..." when voice.isListening. However, the user can still type while voice is active — there's no lock preventing simultaneous voice recognition and keyboard input, which could conflict.

7. The "Voice On/Off" toggle button and the VoiceButton (microphone) are separate controls. voiceMode (toggle) controls TTS auto-read, while VoiceButton triggers speech recognition. These two concepts (STT trigger vs TTS playback mode) may confuse users.

8. No character/token limit indicator. Very long messages sent to the LLM could fail silently with a generic error.
